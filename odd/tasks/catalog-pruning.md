# Catalog pruning

## Objective

Provide a deterministic, offline pruning plan for low-scoring offers and provider-specific keyword series, using only metrics already stored by jobscout.

## Problem and why

The roadmap calls for deactivating the worst-scoring quarter of offers and finding a low-collateral cut of keyword searches. Analytics already aggregate each series by `(provider, query)`, while Tecnoempleo has high repeat-sighting rates and lower scores. A global term deletion would incorrectly affect the same query on other providers.

## Scope and constraints

- Keep offers and keyword series source-specific where applicable; pruning `query|tecnoempleo` must not prune `query|linkedin`.
- Use existing `overall_score` for offer ranking and existing keyword metrics (`avg_score`, `top5_avg_score`, `top10_avg_score`, `duplicate_rate`, and `human_apply_rate`) for the plan. Do not create a composite score, schema, or metric.
- Rank keyword cuts independently within each provider by ascending `avg_score`; use `floor(25% * eligible_series_count)` so a small provider group is never over-pruned. Break ties deterministically by query, and present the other existing metrics as context, never as invented zero when absent. Deactivate only offers explicitly selected with `--apply`; the default is a read-only preview.
- The user withdrew the three-comparable-cycle condition. Do not apply a cycle-count gate.
- Do not reduce Tecnoempleo's page/item caps. Stored result-position analysis shows later-ranked results score lower, but repeat sightings remain high across ranks; a first-page cutoff is not an evidence-backed duplicate fix and conflicts with the repository's collection-cap policy.
- **Hard rule from the owner (2026-09-29): never retire a query that would cost a single good offer.** Before retiring any `(provider, query)`, measure the active offers it alone surfaced (offers no other query of that provider found). If any of those score >= 45, keep the query. The owner rejected retiring `Platform Engineer|linkedin` (30 unique offers, 4 good) and `devops|tecnoempleo` (18 unique, 2 good) for exactly this reason. The no-new-metrics constraint stays, so the "good" threshold reads the existing `latest_evaluations.overall_score`.
- Retirement list, after the 2026-09-30 unique-offer audit: Tecnoempleo — `Platform Engineer`, `Azure Security Engineer`, `IAM Engineer`, `Junior Cloud Security Engineer` (0 unique), `Security Infrastructure Engineer` (2 unique, 0 good); LinkedIn — `Identity and Access Management Engineer` (3 unique, 0 good), `IAM Engineer` (5 unique, 1 good, accepted earlier). **Restore** `Cloud Security Engineer|linkedin` (0 unique) and `Platform Engineer|linkedin` (30 unique, 4 good). **Keep active** `Cloud Security Engineer|tecnoempleo` (7 unique, 2 good), `Identity and Access Management Engineer|tecnoempleo` (8 unique, 2 good), and `devops|tecnoempleo` (18 unique, 2 good), because each costs good offers and the hard rule forbids retiring them. Record retired status/reason in the source-level registry and task history, and reject future plans/searches for these exact normalized pairs, including dry runs. The same literal queries remain available on providers not listed; existing search history is not deleted.
- Default dashboard output includes every active offer; deactivated offers remain in SQLite history but are excluded by the active-offer query. Preserve an explicit `--top` limit for users who want a smaller report.
- Retired series must not read as active searches in the dashboard: the keyword table and the three top-keyword lists (`top_quality`, `top_yield`, `top_human`) exclude them by default, while the payload still marks every series with a truthful `retired` flag (date and reason included) and `summary.keywords` keeps counting every analyzed series. Existing SQLite rows are untouched; this is a display decision only.
- Keep SQLite history; use the existing offer deactivation path. Do not run the apply operation against the user's database during implementation.
- Strict TDD is enabled by project testing-capabilities memory; test runner: `python -m pytest -q`.
- No network access, install, commit, or push.

## Acceptance criteria

- The read-only plan ranks active scored offers and keyword series deterministically without changing database rows.
- Keyword candidates remain separate by provider and use only existing data; missing human approval data stays unavailable.
- Applying the offer plan deactivates only the selected active scored offers and preserves their history; the plan never selects more than `floor(25% * scored_active_offer_count)`.
- Only the explicitly authorized low-collateral provider-query pairs are blocked; the same queries on unlisted providers remain available, and past analytics rows remain visible as history.
- A keyword candidate reports `unique_offers`/`unique_good_offers`, and no pair that alone surfaced a good offer (`overall_score >= 45`) is ever proposed; it is reported as held back instead.
- Dashboard default includes all active offers, excludes deactivated offers, and retains the explicit `--top` option.
- The dashboard keyword table and top-keyword lists exclude retired series by default, each series carries a truthful `retired` flag with date/reason, `summary.keywords` still counts every analyzed series, and an all-retired table falls back to the existing empty state.
- No new metric/schema is added, and no page/item cap is lowered.
- Tests prove preview is non-mutating, apply is bounded/deterministic, and provider-specific series are not merged.
- Both READMEs describe the command and safety behavior; `NEXT_STEPS.md` no longer requires three cycles.
